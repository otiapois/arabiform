# ArabiForm M8 独立验收

**v0.8.0 在干净主线通过全部八项验收。** 真实 Edge 的 72 个场景全部通过，包括 M1–M7 的 66 个和 M8 的 6 个。容量表和 CSV 的数字与字形排版实测一致，带印打印页通过 4× 核验，可编辑 PDF 字节保持一致。500 行名单在桌面和手机模拟视口分别用 752 和 887 ms 完成重启后的预检。

2026-11-27，实测提交为 `ecb1afe6d7b890b942e9edb24a0565f2910cb59f`。环境使用 Node 24.22.1、npm 11.11.0、Python 3.13.11、PyMuPDF 1.26.7 和 Microsoft Edge 124.0.2478.80。[M8 合同](../tasks/M8-scale-watermarks-capacity-inspector.md)

## 500 行处理

浏览器另用一份 500 行合成 CSV，每行含带附标的阿文姓名、拉丁字母及前导零编号，故意把第 203、499 行姓名写得过长。两个视口都先在非零进度处取消，等待原 Worker 关闭并检查导出禁用，再由新 Worker 从保留的文件重新开始。按 `/` 聚焦搜索并输入 `synthetic-00500`，选中第 500 行，核对可见 PDF 预览和原值 `00500`、`سَلْمَى QA 00500`。下载的审计 JSON 逐行核对了全部 500 个编号、文件名与状态，结果均为 498 行就绪、2 行需复查。[实测用例](../../tests/e2e/m8-scale-print-capacity.spec.ts)

| Edge 视口 | 首次取消 | 重开至 498 行就绪 | 键盘搜索及匹配确认 | 搜索前后读到的进度 | 原 200 份 ZIP 下载 |
|---|---|---:|---:|---|---:|
| 桌面 1440 × 900 | 25 / 500 | 752 ms | 72 ms | 25 → 25 / 500 | 3,182 ms |
| 手机 390 × 844 | 25 / 500 | 887 ms | 91 ms | 25 → 25 / 500 | 3,242 ms |

两次搜索在同一批 25 行的显示窗口内完成，返回匹配行后预检仍在运行。耗时取本次主线运行的单次观测。手机阿语容量表的可见区域为 343 CSS px，736 px 宽的表格可在区域内横滚，整个页面保持 390 px。

预检每批 25 行，核心基准另用 404 ms 处理了 500 行，490 行通过、10 行标记，20 批、19 次让出执行机会、只解析一次模板，预检期间 PDF 保存调用为零。逐行排版的字形与布局仅在该行计算时使用。工作线程保留名单、模板和诊断，按需生成所选预览或正在写入的输出行，同一线程串行处理预览和导出。ZIP 按 1 MiB 块组装最终归档。输入、诊断、合并文档和最终下载仍随内容增长。本次没有测量浏览器进程或设备的峰值内存。[预检与取消](../../src/core/worker/batch.ts) · [导出](../../src/core/pdf/exports.ts) · [核心基准](../../tests/core/m8-batch.test.ts)

## 本轮发现与复测

1. 独立下载的 Workshop 正文使用深灰墨色。旧像素检查要求原页必须有纯黑像素，同一对 PDF 在旧校验器失败、修复后通过。无印页 SHA-256 为 `bfcde68a916964a790ee6fd914843be9f3a4b84512e3e03aa9f0067f87e11494`，带印页为 `57dbfa94ffae6a862d1b61ec44bf62d452994631be39aa962785a1fed739b18f`。回放收据保存在主工作区 `test-results/m8-evidence/red-workshop-stamp/`。
2. 200 行可编辑 ZIP 首次移到按需生成后超过原有 15 秒预算。复用完整嵌入字体后，单次桌面仍需 14.757 秒。对已压缩 PDF 使用 ZIP 的存储模式后，逐份写入最终归档。首轮完整主线 `eb2af39` 通过 72/72。随后的 `c5fb7dd` 复跑暴露出 3 项首个非零进度等待超时，最终为 69/72。初始零进度占用了 80 ms 显示窗口。跳过重复的零值后，独立观测仍发现 10 次中有 4 次 Worker 发出了 25 至 200 的消息，而 DOM 直接从 0/200 进入完成状态。改为同步提交第一次非零中间值后，10/10 次均在真实结果前读到 25/200。其中 6 次从 25 到 200 只用了 3–5 ms，逐动画帧采样观察到中间值的为 4/10。后续进度继续节流。失败快照在 `test-results/m8-evidence/initial-progress-red-c5fb7dd/`。[界面修正](../../src/web/useBatch.ts)
3. 原有 M2 两个用例调整了同步时机。搜索开始前仍须观察真实非零中间进度，搜索返回后接受单调进度或已确认的 200 行就绪。回放覆盖 25→25 和 25→200 两种路径。相邻的短批取消曾在 Playwright 滚动到可见按钮时恰好完成。该用例现在预订 Worker 关闭事件，在界面有非零中间进度且按钮可见可用的同一轮触发处理器，继续验证暂停、重开、替换名单以及 `00999` PDF。500 行预检和 200 行合并导出的正常指针点击取消另有真实场景。其余 64 个旧场景保留原断言。[两处同步调整](../../tests/e2e/m2-batch.spec.ts)
4. 旧图库断言发现，拆分容量模块时 PDF 入口块被重命名。生产构建恢复了可识别的 `pdf-` 名称。桌面容量表还继承了队列第 4 列的 37% 宽度；修复将列宽限定到队列，手机增加滚动提示。相关独立截图和空载请求按修复后的界面重取。[构建配置](../../vite.config.ts) · [经验记录](../../LESSONS.md)

四项 M8 经验分别按一个里程碑周期计数。此次没有新规则达到三个独立周期的晋升门槛。快速预检的修复前后原始时间线在 `test-results/m8-evidence/progress-burst-proof/`，严格 200 行场景的三轮双视口日志在 `strict-200-observer-repeats/12-cases.log`。[既有代码标准](../code-standards.md)
